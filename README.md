# Практична робота №5 — SPA на чистому JavaScript

Односторінковий додаток на базі сторінки альбому з попередніх робіт. Відкрити `index.html` у браузері.

## Що реалізовано

- **Розділи:** три `<section>` — `#catalog` (трек-лист), `#details` (про альбом), `#feedback` (форма відгуків). Початково видно лише перший, інші приховані класом `.is-hidden { display: none; }`.
- **Навігація:** `<nav>` з посиланнями `href="#catalog"`, `#details`, `#feedback`.
- **Маршрутизація (підхід А):** `window.addEventListener('hashchange', render)`. Функція `render()` читає `location.hash`, показує потрібну секцію через `classList.toggle('is-hidden')`, підсвічує активний пункт меню класом `.is-active` і `aria-current="page"`, змінює `document.title`. Невідомий хеш веде на «Каталог».
- **Індикатор глобального стану:** у `<header>` — `<audio controls>` і таймер сесії на `window.setInterval()`. При переходах між розділами музика не зупиняється, а таймер не скидається.
- **Обмеження:** тільки Vanilla JS, без бібліотек; без `document.body.innerHTML`; без `onclick` — лише `addEventListener`; працює без сервера.

## Аудит у DevTools Network

1. Відкрити сторінку, натиснути F12 → вкладка **Network**, фільтр **Doc**.
2. Увімкнути трек, перейти по всіх розділах.
3. Результат: у списку один запит `index.html` (первинне завантаження). Під час переходів нових запитів типу Doc немає, змінюється лише хеш в адресному рядку. Музика грає далі, таймер рахує без скидання.

## Відповіді на контрольні запитання

**1. Відмінність життєвого циклу MPA і SPA.**
У MPA кожен перехід — це новий GET-запит, браузер вивантажує старий документ і будує новий з нуля (парсинг HTML, CSS, виконання скриптів). У SPA документ завантажується один раз, а при переходах JavaScript лише показує чи підміняє потрібну частину DOM. Сторінка не перезавантажується.

**2. Що видно у Network.**
При переходах між окремими HTML-файлами (MPA) на кожен клік з'являється новий запит типу Doc і повторні запити до ресурсів. У реалізованому SPA після першого завантаження нових запитів Doc немає — змінюється тільки фрагмент URL (`#details`), який на сервер не надсилається.

**3. Чому в MPA руйнується стан.**
Стан JS (змінні, таймери, медіа) живе в пам'яті конкретного документа. При переході браузер знищує цей документ разом з усіма об'єктами, обробниками і `<audio>`, а новий документ стартує з нуля.

**4. CSR (чистий SPA) проти SSR і SSG.**
- CSR: швидкі переходи після завантаження, легкий сервер, зберігається стан. Але перший показ повільніший (треба завантажити й виконати JS), а пошуковик бачить майже порожній HTML — гірше для SEO.
- SSR: сервер віддає готовий HTML на кожен запит — швидкий перший показ і добре SEO, але більше навантаження на сервер.
- SSG: HTML генерується заздалегідь під час збірки — найшвидша віддача і добре SEO, але погано підходить для даних, що часто змінюються.

**5. Гідратація.**
При SSR сервер віддає готовий HTML, який одразу видно, але він «мертвий» — без обробників подій. Гідратація — це коли в браузері завантажується JS-фреймворк, проходить по вже готовій розмітці, зв'язує її зі своїм станом і навішує обробники. Після цього сторінка стає інтерактивною, як звичайний SPA.

## Висновок

У роботі я порівняв модель MPA і SPA та реалізував односторінковий додаток на чистому JavaScript. Навігація побудована на хеш-маршрутизації через подію `hashchange`: секції перемикаються класом `.is-hidden`, активний пункт меню підсвічується, а документ не перезавантажується. Аудіоплеєр і таймер сесії в шапці підтвердили збереження глобального стану — музика і відлік не перериваються при переходах. У вкладці Network видно лише один запит типу Doc при першому завантаженні, що підтверджує клієнтську маршрутизацію без звернень до сервера за новими сторінками.
